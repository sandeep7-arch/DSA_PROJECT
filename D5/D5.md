## 1. The question we are answering

A Fenwick tree is often taught for prefix sums. The same small tree idea can also remember the largest value in a prefix, as long as values only increase. This report asks a very specific question: what goes wrong when a sensor reading that used to be largest is assigned a smaller value?

The short answer is that a maximum summary remembers the winning value, but it does not remember all the information needed to undo that win. When the winner is lowered, the old summary may need to be replaced by the runner-up. The Fenwick cell cannot discover that runner-up from the old maximum alone.

## 2. A tiny example

Start with the two readings `[9, 4]`. The maximum of the first two readings is 9. Now assign the first reading to 1. The correct readings are `[1, 4]`, whose maximum is 4.

The increase-only update rule says: for each Fenwick cell that contains this position, keep the larger of the saved value and the new value. In this example it compares the saved 9 with the new 1 and keeps 9. The stored answer is now stale: it claims 9 is still present even though the value 9 was removed.

This is not a bug that can be fixed by changing `max` to another one-line expression. A cell storing just `9` cannot tell whether the old 9 was the only winner, whether there was another 9, or whether the best remaining value is 8, 4, or something else. It lacks the history needed to choose a replacement.

## 3. What the program does

The program creates values in descending order, so the first position begins as the maximum. On each round it finds the current maximum, lowers it by one, and rebuilds a prefix-maximum Fenwick tree from the changed array. It prints the rebuilt prefix maximum beside a direct scan of the array. Those two values should agree after each rebuild.

The rebuild is deliberate. It is the simple way to restore correct summaries when using this increase-only structure. The code uses a basic vector, loops, a class, and integer arithmetic. The tree's update loop moves to the next Fenwick cell with `i += i & -i`; its query loop moves to the containing prefix cells with `i -= i & -i`.

## 4. Why the sequence is adversarial

An adversarial sequence is an input chosen to expose a weak point repeatedly. Here the sequence repeatedly changes the current maximum. Every such assignment invalidates stored maximum information. A program that insists on using this baseline must rebuild after every decrease to stay correct.

With the simple constructor in this example, rebuilding inserts all `n` values and each insertion visits up to `O(log n)` cells. One rebuild therefore takes `O(n log n)` work. If there are `d` decreases, the repeated-rebuild work is `O(d n log n)`. A specialized Fenwick build can reduce the rebuild to `O(n)`, but it still has to revisit the whole array after each decrease: `O(d n)`.

This is a cost of this prefix-only baseline and its missing decrease operation. It is not a proof that every Fenwick-based range-maximum design is slow. The project brief's Dima–Ceterchi two-tree structure is a different, more advanced design and needs its own implementation and proof.

## 5. How to run it

```sh

./d5_demo
```

Enter an array size and a number of decreases when prompted. For example, `5 7` builds five readings and performs seven decreases. The array values are generated by the program, so no extra input file is needed.

## 6. What to say in a presentation

“For an increase, a Fenwick maximum cell can safely keep the larger of its old value and the new value. For a decrease, that rule cannot remove the old winner. The cell stores the maximum, not the second-largest value or the identity of every value that produced it. So this simple structure must rebuild to recover correct answers. That limitation is why maximum does not work like prefix sum subtraction.”
